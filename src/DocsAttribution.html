Overview

The B-Bucks Economy Scripts project is a Google Sheets-based classroom economy system designed for managing digital money, service transactions, investments, and historical records in a school or club environment.

Important usage note: start with the spreadsheet menu, not the raw sheet cells. Every major function is designed to run through the banking tools so the ledger, validation, and history all stay consistent.

Project Scope

This system combines spreadsheet automation, Apps Script backend functions, and browser-style dialog interfaces to create a complete virtual banking experience. It gives an instructor control over student accounts, school-facing transactions, ledger visibility, and analytical tooling without leaving Google Sheets.

The project is built around a set of specialized interfaces that open from the spreadsheet menu and connect to shared utility logic, cached sheet reads, and structured transaction handling.

First-Time User Walkthrough

Recommended order for new users: do not start by editing raw cells or changing settings. Open the menu, confirm the spreadsheet structure, then run the classroom actions through the proper banking tool so the history, balances, and validation stay aligned.
  1. Open the app from the spreadsheet menu: in Google Sheets, open “The Central Bank of Banderas.” This is the main entry point for all system actions.
  2. Confirm the workbook is ready: if the spreadsheet does not already contain the required student or banking sheets, use the setup/import helper to create or populate the sheet structure before entering balances.
  3. Set up or review the student list: make sure the names or IDs used in the economy are present and correctly formatted. This affects every later transaction and lookup.
  4. Open Manual B-Bucks first: this is the place to apply starting balances, corrections, or teacher-led adjustments. It is the safest place to begin because it establishes the initial financial baseline.
  5. Create a normal money event: use Services & Transactions when a student earns, pays, spends, or receives a fine. This is the core day-to-day flow for classroom transactions.
  6. Use Investment Banking for growth behavior: if the economy has savings, interest, or portfolio-style earning, use this section to track deposits and investment activity without disrupting regular ledger entries.
  7. Review the records before closing a period: open Transaction Records to confirm what happened and make sure the balance history matches the classroom reality.
  8. Check the analytics: once entries are validated, use Historical Analytics to review trends, totals, and financial movement across time.
  9. Only change settings when needed: open Banking Settings for rate logic, date policy, and maintenance tasks. Adjustments here affect the system rules, so they should be made intentionally and carefully.

Core Workflow

The user opens a menu item from the custom “Central Bank of Banderas” menu in Google Sheets. Each menu action launches a modeless dialog, which then sends requests to Apps Script functions via client-side callbacks. The server code validates data, reads or writes to the spreadsheet, updates records, and returns summary information back to the UI for display.

In practical terms, the workflow usually looks like this:

  1. Open a banking tool from the spreadsheet menu.
  2. Select a student, range, date period, or transaction type.
  3. Enter or confirm a financial action such as transfer, adjustment, interest, or expense.
  4. Apps Script validates and writes the data to the governed sheet structures.
  5. The UI refreshes, showing updated totals, logs, charts, or historical summaries.

System Components

The product is organized into a few major areas:

  • Manual Balance Management: direct updates to student balances and supporting notes.
  • Service Transactions: income and expense-style entry workflows.
  • Investment Banking: controlled growth and yield-based account operations.
  • Records & Analytics: searchable histories and trending metrics.
  • Settings & Maintenance: configuration for banking logic and automated rules.

Balance Management

The manual balance system is the backbone of the classroom economy. It allows an administrator to add, subtract, multiply, divide, and override balances with precise control and a visible audit trail.

How to use it: open the Manual B-Bucks tool, pick the target student or range, enter the amount or operation, and add a note before submitting. This keeps the change visible and auditable.

Manual Adjustments

Adjustments can be made through quick action buttons, custom amounts, and selected account ranges. Each change can include a descriptive note so the action remains transparent and reviewable later.

This is useful for events like bonus payouts, deductions, student transfers, corrections, or teacher-led overrides. The interface is designed to minimize error by pairing numeric input with direct account targeting and a confirmation workflow.

Tax and Rule Logic

Tax and percentage-based deductions are handled centrally so the project can apply the same financial rules consistently across student records and periods. This is especially important when a balance adjustment is not a flat number but a percentage-based calculation.

When taxes or reductions are triggered, the system preserves floating-point math as closely as possible, reducing the risk of rounding issues that can distort classroom balances.

Auditability and Search

Because educational economies need traceability, balance changes are intended to be logged along with a date, category, and reason. This makes it easier to revisit a transaction, correct a mistake, or explain why a balance was modified.

Services & Transactions

The services page supports income and expense-style entries that mirror real-world classroom economy behavior. This is where salary-like earnings, fines, purchases, and reimbursements are usually recorded.

Use this when: a student earns money, pays a fee, buys an item, or needs an approved exception. The services tool is designed to record those events cleanly and consistently.

Income & Expense Entries

Users can submit a transaction type, amount, and contextual data to reflect a money event. The system handles these interactions through client-side dialogs and server-side validation before committing changes to the sheet.

Validation & Overrides

Some situations require a balance override or a forced transaction when a student is below zero or an item has been manually approved. The system is designed to support both standard validation and teacher override workflows.

That balance between process and exception handling is what keeps the economy structured without becoming too rigid.

Investment Banking

The investment banking page manages more advanced monetary behaviors such as savings or growth-based accounts. These features are useful when the class economy includes deposits, rate-based earnings, or long-term accumulation scenarios.

Use this when: the class economy includes savings, investment periods, or rate-based growth. This tool tracks deposits and earning behavior without removing the teacher from the decision loop.

Yield Rates

Yield rate controls define how much growth is applied to holdings over time. The system can combine this with ledger data to calculate recurring returns, investment totals, and expected account values.

These functions let the teacher phrase the economy as more than a simple ledger: it becomes a simulation of interest, compounding, portfolio behavior, and student financial planning.

Portfolio Principles

Investment logic usually operates on balances that are tied to a learner, a period, or a predefined item category. The result is an ecosystem where directing funds into a growth cycle causes later updates while preserving the source-of-truth spreadsheet values.

Transaction Records

The transaction records page is the readout for the financial history of the economy. It allows administrators to search, filter, and review all money movement that has taken place within the portfolio.

Critical review step: before closing a banking period, always check the records page. This is where you confirm the teacher-approved actions and catch mismatches before they affect analytics or balances.

Filtering & Search

Searchable records are essential when the teacher wants to inspect a single student, a date range, or a specific transaction category. This makes the system useful in both daily operations and retrospective reviews.

Audit Trail

Every transaction is treated as part of a long-term recordbook. This makes it easy to review what happened, when it happened, and whether the action was aligned with school policy or an approved exception.

Historical Analytics

The analytics view turns raw ledger entries into usable visual context. Instead of scanning rows manually, the teacher can view trends over time and compare how balances, incomes, and expenses evolve across periods.

Best practice: use analytics after transactions are posted and verified. This lets the trends reflect the true state of the economy rather than temporary edits or unconfirmed entries.

Charting & Trends

Chart-based summaries help track the rise and fall of financial activity in a way that is easier to communicate to students or administrators. This provides a high-level summary of totals, changes, and recurring patterns.

Metric Filters

Users can focus the analytics panel by selecting a period, series, or metric column. This converts a large dataset into a digestible series of financial insights that are relevant to the point being reviewed.

Banking Settings

Project settings configure the rules that define how the virtual banking environment behaves. These include interest, restrictions, date boundaries, and the maintenance-style actions that keep the system healthy.

Admin warning: only change banking settings after reviewing the impact on rates, date windows, and historical comparisons. A policy change can affect every transaction unless it is applied deliberately.

Banking Policy

Policy settings define the assumptions behind the economy. This can include rate logic, restrictions on actions, and expected periods for collection or evaluation.

Maintenance Tools

Maintenance options exist for cleaning, refreshing, or resetting records, making it easier to keep the system organized over time. These controls are especially important when the economy is used repeatedly across different terms or grading cycles.

Data Import & Sheet Setup

The import helper is used to create or populate student sheets based on a dataset or template. This reduces the manual overhead of entering names and structure by hand.

Setup shortcut: if a sheet is missing or the workbook was reset, use the import helper before running any balance or transaction logic. This restores the expected layout and reduces broken references.

Template Import

The system can create new sheets from an existing template when a required sheet is missing. This keeps the workbook consistent and reduces setup errors during onboarding.

Sheet Structure

Reliable system behavior depends on consistent spreadsheet structure. Each sheet must follow the expected naming, position, and formatting conventions, so the script can read and write values consistently.

Caching & Performance

The project is designed to minimize unnecessary spreadsheet reads and repeated data processing. This matters because Google Sheets operations can become slow or expensive when dozens of balances, histories, and UI refreshes are triggered in a short period of time.

Developer note: when debugging data problems, always clear or refresh cache state before assuming the sheet content is the issue. Many stale values come from cached ranges rather than the active workbook itself.

CacheService Strategy

The system uses Apps Script caching to temporarily hold processed values such as lookup tables and shared data maps. Instead of re-reading the same sheet ranges every time a dialog refreshes or a user requests a calculation, the script can reuse stored values from the cache.

const cache = CacheService.getScriptCache();
const cachedData = cache.get("BALANCE_CACHE");

This dramatically reduces repetitive access to the Google Sheets API and improves response time for the classroom experience.

Direct Range Block Selection

Rather than reading arbitrary cell values one at a time, many utility functions operate on direct ranges of data and convert them into JavaScript arrays. This is a more efficient pattern because it keeps the workbook interactions compact and allows the logic to work with matrix-like blocks of rows and columns.

By using these direct block operations, the app reduces overhead while still preserving the ability to calculate, compare, and format financial data in a structured way.

Developer Deep Dive: Lower-Level Flow

From a development perspective, the app is structured around a few repeating patterns:

  • UI actions call server functions from the menu-driven dialogs.
  • Utility modules centralize spreadsheet access, validation, caching, and transaction rules.
  • Exposed apps-script functions convert client input into workbook-safe data structures.
  • Transaction logs and analytics depend on consistent headers, row alignment, and naming conventions.

When debugging a new feature, begin at the menu trigger, then follow the server call, then inspect the utility layer, and finally validate the workbook output. This reduces confusion when data is missing, malformed, or stale.
