User Guide

    Start Here

    This system runs your classroom bank inside Google Sheets. Students earn and spend B-Bucks, can lock money in a savings account called a CoD, and everything is written to a history you can search and undo.

    The one rule: change money through the The Central Bank of Banderas menu, not by typing into cells. The menu tools record every change, keep the totals correct and make it possible to undo a mistake. Typing straight into a cell works, but it leaves no history.

    The menu

    Open the spreadsheet and look for The Central Bank of Banderas at the top (next to Help). Each item opens a window that stays open while you keep working in the sheet.

    Menu itemUse it to…
    Open Manual B-Bucks ModifierGive or take away money by hand: bonuses, fixes, one-off changes.
    Open Service ProviderCharge for items or pay for jobs from your price list (the "Services" sheet).
    Open Investment BankingPut a student's money into a CoD, take it back out, and preview what it will earn.
    View Transactions RecordsSearch everything that has happened, and undo mistakes.
    View Historical AnalyticsChart how the class economy changes over time.
    Banking SettingsDates, tax and interest rates, rules, and the maintenance/reset tools, including the student portal setup.
    Documentation & AttributionThis guide.

    Words you will see

    WordMeaning
    B-BucksThe class currency.
    Period sheetOne tab per class period ("Period 1", "Period 2"…). Each lists that period's students.
    BalanceThe cash a student has to spend right now. It is worked out by the sheet from the other columns, so don't type over it.
    Earnings / ExpendituresRunning totals of money earned and money spent.
    CoDA savings account. Money put in earns interest each week. It is locked for a set number of days after it is opened (the withdrawal window).
    Admin OverrideA checkbox that lets you do something the rules would normally block. Use it deliberately.
    QuarterOne of four grading terms (Q1–Q4). Prices on your Services sheet can differ by quarter.

    A typical school day

    1. Open the sheet and the tool you need from the menu.
    2. Click the student(s) in the right Period tab (see selecting students).
    3. Apply the change (add income, charge an item, adjust a balance).
    4. Glance at the Activity Log in the same window to confirm it was recorded. Made a mistake? Click it in the log and press Undo.
    New here? Read First-Time Setup next, then Adding & Removing B-Bucks.

    First-Time Setup

    Do this once at the start of the year (or semester). It takes about ten minutes.

    1. Set the dates

    1. Menu → Banking Settings.
    2. In Important Dates, fill in the start and end of each quarter, plus the banking and investing periods.
    3. Click Save on that card.
    Why the quarter dates matter: the Service Provider reads them to choose the correct price column automatically. If they are blank it stays on Q1. An end date counts through the whole last day.

    2. Import your students

    This builds one tab per period and fills in the names. It also stores each student's ID in a hidden column of the tab (column L unless you change studentIdCol in the Advanced Technical Settings), which is what the student portal uses to recognise a student's email. Do not put anything else in that column.

    1. Export your roster as a .csv or .txt file. Gradebook rosters (each period starts with a line such as 1 - Period 1) and Attendance Class Rosters (a Period,... column line, then the period number and its students) both work. Repeated sections, Fall and Spring copies and duplicated students are merged, so each student appears once per period.
    2. Banking Settings → Maintenance → Import All Students.
    3. Choose the file. A preview appears; check the periods and names.
    4. Press Import Data, then confirm.
    Your students' data is kept. If a Period tab already exists and mostly matches the file (at least half of the file's students, or half of the tab's students, are found by ID or by name), the tab is updated in place: everyone keeps their row and balances, students who are missing are added at the bottom, and IDs are filled in for students imported before IDs existed. Nobody is removed or renamed. When the import finishes it tells you, period by period, how many were kept, added and filled in.
    A tab that does not match the file is still replaced (deleted and rebuilt from the Template tab), and its balances are lost. Two students with the same name but different IDs are never merged: the newcomer is skipped and listed in the summary. If column L already holds something of yours, the import refuses to touch that tab and tells you to pick another column.

    3. Fill in your price list

    Open the Main Services tab. Each row is one item or job:

    ColumnPut…
    Item nameWhat students see, e.g. "Homework pass".
    CategoryIncome (students receive money) or Expense (students pay money).
    Price Q1–Q4The price for each quarter. Leave a quarter empty to hide the item in that quarter.
    Limit Q1–Q4Optional maximum per person for that quarter.

    4. Check rates and rules

    Still in Banking Settings, review Standard Percentages (income tax, investment withdrawal tax, weekly interest), Mandated Policies (withdrawal lockout days, whether debt is allowed) and Limits. Save each card after changing it.

    Changing the income tax rate rewrites the Net Income formula on every Period sheet immediately.

    5. Turn on the daily snapshot (optional)

    The charts in Historical Analytics are built from a daily snapshot of the economy. Your technical contact can schedule it to run automatically (see Developer Setup). You can also take one yourself any time: Banking Settings → Maintenance → Record Daily Data Snapshot.

    Adding & Removing B-Bucks

    The Manual B-Bucks Modifier is for anything that isn't on your price list: a bonus, a correction, a one-off fine.

    Selecting students

    These tools act on whatever you have highlighted in the sheet. Click the cell(s) you want to change on a Period tab. You can select several students at once: drag down a column, or hold Ctrl (Cmd on Mac) and click separate cells.

    Check the highlight before every change. The window says nothing about who is selected; it applies the change to the selection. The Activity Log shows who was affected afterwards.

    Quick buttons

    • +1, +2, +5, +10 / −1, −2, −5, −10: add or subtract that many B-Bucks from each selected cell.
    • ×2, ×5 / ÷2, ÷5: multiply or divide the selected cells' current value.

    Custom amount

    Type into the box, then press Enter or the button:

    TypeResult
    10Add $10
    -5Subtract $5
    *2Double the value
    /4Divide the value by 4

    Always add a reason

    The Transaction Reason box is optional but worth using. The text appears in the Activity Log and the Transaction Records, which makes it easy to explain a change to a student later.

    Undoing a change

    1. In the Activity Log (right side), click the entry or entries you want to reverse. Selected entries are highlighted.
    2. Press Undo.

    Undo doesn't delete the original line. It applies the opposite change and logs that too, so the history always tells the full story.

    Income & Expenses (Service Provider)

    Use this when the money event is on your price list: paying for a job, charging for an item, a fine.

    How to use it

    1. In the sheet, select the student(s) on their Period tab.
    2. Open Service Provider. Use the left card Add Income to pay students, or Add Expense to charge them.
    3. Pick the Item and the Quantity. A preview line shows exactly what will happen (for example "Base: $5 × 3 = −$15").
    4. Press the Add button. The Activity Log updates.

    Income is added to each student's Earnings; expenses are added to their Expenditures. The balance follows automatically.

    The quarter picks itself

    The Quarter dropdowns on both cards are set to today's quarter when the window opens, using the dates in Banking Settings. If the window stays open past a quarter change, it moves on its own, within five minutes or the next time you click back into it.

    • Between two quarters (a break), the quarter that most recently started stays selected.
    • Before the first quarter starts it shows Q1; after the last one ends it stays on Q4.
    • If you choose a quarter yourself, that dropdown is left alone from then on, so a manual choice is never overridden.
    Prices come from the quarter shown in the dropdown, so after a quarter changes, check the price in the preview line before charging.

    Not enough money?

    If an expense would push a student below $0 you will see "Insufficient funds" and the change is refused, listing who is short. Tick Override Restrictions if you want to let it through anyway (a student then owes the bank).

    Max per person

    When an item has a number in the Max/Person column for the chosen quarter, a green box under the quantity shows how many of that item each selected student has left (the students with the fewest left are listed first). It turns red when the quantity you typed is more than someone has left, and the purchase is refused. Override Restrictions lets it through anyway, the same tick box that allows a negative balance.

    • Purchases are counted from the Transactions Records, per student and per quarter, so undoing a purchase gives the allowance back.
    • The quarter is decided by the date and time of each purchase, using the quarter dates in Settings.
    • Turn off enforceServicesLimits in Settings to show the counts without blocking anything.

    Max per class

    The Max/Class columns work the same way for a whole class: the box shows how many of the item the class has left this quarter, counted across every student on that period's sheet. A class is the period number in the sheet name, and buying for several selected students uses up the quantity once per student. Override Restrictions bypasses it too.

    The note on the Expenditures cell

    Hover the Expenditures cell to see the list of purchases that make up the number. The note is rebuilt from the Transactions Records every time they change, to the second, so it always matches the log and an undone purchase disappears from it. Do not edit the note by hand, the next purchase or undo rebuilds it. If notes ever look off, use Rebuild Expenditure Notes in the menu. It rewrites the note of every student that has expenditures in the log and leaves students with nothing in the log untouched.

    Investments (CoDs)

    A CoD takes cash out of a student's balance and grows it with weekly interest. When it is withdrawn, the winnings go back into the student's cash (minus a withdrawal tax).

    Choosing a student

    Pick the Period, then the Student. The overview shows:

    • Available Cash: the student's current balance.
    • Current CoD: what their CoD is worth right now after interest and tax.
    • Total Available: cash plus CoD.
    • CoD Final Deadline: when the withdrawal window ends.

    The withdrawal window

    After a deposit, the CoD is locked for the number of days set under Mandated Policies (default 14). While locked, the Deposit, Withdraw and "Deposit Cash w/ CoD" buttons are disabled. Tick Admin Override to bypass the lock for one-off exceptions.

    Depositing

    1. Select the student.
    2. Type an Amount, or press Deposit All Cash to fill in their whole balance.
    3. Press Deposit.

    Deposit Cash w/ CoD (roll everything over)

    This fills the amount box with cash + current CoD, so the old CoD is cashed in and re-invested together with the cash. It works under these rules:

    • The CoD must be outside its withdrawal window, or Admin Override must be ticked.
    • The deposit can use the balance and the CoD together. It no longer matters that the cash alone is smaller than the total.
    • If the window is still open and the override is off, you get a warning explaining that depositing everything isn't possible, and nothing changes.
    • If the amount is larger than cash + CoD, you get a warning showing the cash, CoD and total available. With Admin Override you may go past it (the balance goes negative).
    Example: a student has $50 cash and a $30 CoD that is past its window. "Deposit Cash w/ CoD" fills in $80, and the deposit goes through. If the CoD were still locked, you'd be told it isn't possible unless you use Override.

    Withdrawing

    Press Withdraw to cash the whole CoD out into the student's balance. It follows the same lock/override rules.

    The earnings calculator

    The bottom card previews growth without changing anything. Choose a mode (Current CoD, Custom Amount or From Deposit), set the week, and read the projected value. Current CoD starts from the initial deposit amount and counts weeks from the initial deposit date; it is the only mode whose list marks the current week, which is the amount to expect right now. Interest is simple (the same amount each week, not compounding), based on the weekly rate in Banking Settings.

    Transaction Records & Undo

    Every change made through the menu tools is stored here, newest first. This is your audit trail.

    Finding things

    ControlWhat it does
    Search + ScopeType text; Scope chooses where to look (all fields, student, item, type, period, transaction ID or column).
    Period / Student / TypeNarrow to one period, one student, or Income / Spending / Investment. The lists only show choices that exist.
    From / To dateLimit to a date range (both days included). The Period and Student lists adjust to what happened in that range.
    Page / DisplayedWhich page you're on, and how many entries per page (up to 200).
    Reset FiltersClears everything back to the default view.

    The tiles at the top (Total, Income, Spending, Net) always describe everything that matches your filters, not just the page on screen.

    Why paging is quick

    The log can grow to many thousands of entries, so the window only loads the page you're on plus a few next to it, and keeps those ready. Moving to the next or previous page is usually instant. Jumping to a far-off page takes a moment to fetch. Refresh Transactions re-reads the sheet from scratch (use it if you edited the Transactions tab by hand).

    Undoing

    1. Click one or more entries to highlight them.
    2. Press Undo Selected.

    Undo reverses the change on the student's Period sheet and adds a new line labelled "Undo transaction ID …". The original stays in the history.

    Undo works from the amounts recorded in the entry. If the student's value has been changed by hand since then, the result may not be what you expect, so check the new line it creates.

    Historical Analytics

    A line chart of how the economy has changed, built from the daily snapshots plus, optionally, the numbers as they are right now.

    Reading the chart

    • Each point is one calendar day. Points are always in date order.
    • If more than one snapshot was taken on the same day, the latest one is used. They are never added together.
    • The large ◆ diamond labelled "(live)" is today's current value, calculated on the spot. It isn't saved anywhere until the next daily snapshot, so it may move if you reload.

    Controls

    ControlWhat it does
    Metric ColumnsWhat to plot (total balance, total earnings…). Hold Ctrl / Cmd to pick several.
    Sheet / Period ScopeAll Periods (Combined) adds the periods together; (Average) averages them; or pick individual periods.
    Scale TypeLinear, or logarithmic for data that grows fast.
    From / To DateLimit the range shown.
    Include live (now)Show or hide the ◆ live point.
    Reset FiltersBack to the default view.

    If something looks off

    • A yellow notice above the chart means the live point couldn't be calculated (for example, a formula on the Historical Records sheet is broken). The recorded history still shows.
    • No data at all? No snapshot has been recorded yet. Take one from Banking Settings → Maintenance.
    • Old data is missing? Data that was saved with "Save to New Sheet Tab" lives in tabs named Records_…; those tabs are included automatically as long as they still exist.

    Student Portal

    One link for everyone. Students sign in with their school Google account and see their own balance, can invest, request purchases and watch the class leaderboard. You open the same link, go into any student's account to act for them, and approve requests.

    Setting it up

    1. Banking Settings → Maintenance → Student Portal → Set Portal Domain. Enter the email domain your students sign in with. It is stored in the project's Script Properties, never in the code.
    2. Banking Settings → Maintenance → Student Portal → Create Portal Tabs. This adds the Portal Accounts and Expenditure Requests tabs.
    3. In the Apps Script editor choose Deploy → New deployment → Web app. Set Execute as to Me and Who has access to Anyone in your organization. Share the link it gives you.
    Execute as "Me" is required. Students never get access to the spreadsheet itself; the portal works for them on your behalf and only ever shows or changes their own account.

    How a student is found

    Every student email contains the student's ID, and the import stores each ID in a hidden column of the Period tab. The portal splits the part of the email before the @ into runs of digits and links the student whose ID is exactly one of those runs (for example 123456@... or jdoe123456@...). Nobody is guessed from a name. A student on two Period tabs has the same ID on both and gets a switcher at the top.

    • Tabs imported before IDs existed have no IDs yet. Import the roster once more: it fills in the IDs without touching anyone's data.
    • Portal Accounts tab (optional override): one row with Email, Period (3 or Period 3) and Name exactly as on the Period tab, for an email that does not contain the ID.

    A student whose email matches nobody sees a friendly "ask your teacher" message.

    What students can do

    • Home: balance, CoD, spending and the full transaction history, read from the transactions sheet named in Settings (Default Transactions Sheet). Newest first, 15 per page. The whole history is loaded once and the search box (matches the description, type or date), the Income / Spending / Investments buttons and the Newer / Older buttons work on that list in the page, so they are instant. If that tab is missing or renamed, the history shows a message instead. Times are shown with hours, minutes and seconds.
    • Invest: invest cash, withdraw once the withdrawal window is over, and use an earnings predictor like the one in Investment Banking. The portal's predictor also applies the Investment Withdraw Tax from Settings, so each week shows the value before tax and the value after tax (what the student would really get on withdrawing). Students can never use the admin override.
    • Spend: request something from the current quarter's price list. Remaining Max/Person and Max/Class counts are shown, and requests that are still waiting also count against them. Your spending is a read-only record of every log row of type Expense for that student (reversed ones are kept but struck through). Nothing in it can be undone from the portal. Students can cancel a request only while it is still pending; once it is approved, only you can reverse it, in Transaction Records. Each item has an optional Add a note box where the student can write the details in a paragraph (up to 1000 characters). Requests show a status: Pending, Approved, Completed, Denied or Cancelled.
    • Leaderboard: the top ten of their period plus their own rank (cash plus CoD value, names shortened to first name and last initial).

    Approving requests and acting in a student's account

    If you can edit the spreadsheet, the portal shows an Admin tab. Pick any period and student and press Open account. You are then literally in their account: you can invest, withdraw, request purchases and cancel requests for them, under the same rules and caps as the student (no override). A banner at the top reminds you whose account it is, and Exit returns you to your own view. Each action is written to the log with your email and the student's name, and requests you make carry a note saying so. The request list shows pending requests first. Approve charges the student exactly like the Services dialog (logged, counted against the caps, undoable in Transaction Records) after checking the price, balance and caps again. Deny charges nothing. An optional note is saved with the request. Every request row opens a Details section with the student's note, who asked and when. Approved requests stay at the top of the list with a Mark completed button (and an optional note): it sets the status to Completed on the Expenditure Requests tab and fills in Completed By and Completed At, so the sheet itself shows what is done. You can also see the new columns Student Note, Completed By and Completed At there; tabs made by an older version get the headers added automatically.

    Troubleshooting & FAQ

    The menu isn't there

    Reload the spreadsheet tab. The menu is created when the file opens. The first time, Google asks you to authorise the script; accept the prompts.

    A window shows old numbers

    Close and reopen it, or use Banking Settings → Clear Client Cache. In Transaction Records, press Refresh Transactions.

    I pressed a button and nothing happened

    • Did you select a student cell in the sheet first? Quick buttons and the Service Provider act on the selection.
    • Look for a pop-up message. Refusals (insufficient funds, a locked CoD, an unknown student) are explained there.
    • Is the right Period tab active? The selection must be on a Period tab, not the Settings or Services tab.

    The wrong prices appear

    Check the Quarter dropdown, then the quarter dates in Banking Settings. If a dropdown was changed by hand, it won't follow the calendar until the window is reopened.

    "Deposit Cash w/ CoD" is greyed out or warns me

    The CoD is still inside its withdrawal window. Wait for the "CoD Final Deadline", or tick Admin Override. See Investments.

    Architecture Overview

    A Google Sheets bound script written in TypeScript, compiled to plain Apps Script (V8) and pushed with clasp. The UI is a set of modeless HTML dialogs that talk to server functions through google.script.run.

    Layers

     Sheet (Period tabs, Settings, Services, Transactions, Historical Records)
    ▲                                   ▲
    │ SpreadsheetApp                    │ formulas (Balance, Net Income…)
    │                                   │
 src/utils/*.ts  (server, global scope, no modules)
    ├─ GlobalConsts.ts      Tier-0 literal constants (no sheet access)
    ├─ Config.ts            Tier-1 lazy, memoized settings: getConfig()
    ├─ SettingsUtils.ts     Settings sheet <-> typed values
    ├─ BankingUtils.ts      balance / earnings / expenditure edits
    ├─ InvestmentUtils.ts   CoD deposit / withdraw / interest
    ├─ TransactionsUtils.ts append + undo; calls cache hooks
    ├─ TransactionCache.ts  rolling block cache + paged queries
    ├─ QuarterUtils.ts      date -> current quarter
    ├─ HistoricalAnalytics.ts   archive merge + live snapshot
    └─ OnLoadData.ts        menu, dialogs, bootstrap, daily snapshot
    ▲
    │ google.script.run  (JSON in / JSON out)
    │
 src/*.html  (client: BalanceManager, ServicesManager, InvestmentsManager,
              TransactionsRecords, HistoricalAnalytics, SettingsManager, Docs)
    └─ src/utils/ClientToServer.html   callServer / callServerAsync
       src/utils/TransactionWindow.html RollingTransactionLog (client RAM window)

    Request flow

    1. The user picks a menu item; onOpen (in OnLoadData.ts) registered it.
    2. The handler builds an HtmlTemplate, injects bootstrap data (settings, services, investments) and shows a modeless dialog. Transactions are not in the payload; the client pulls them page by page.
    3. The client calls server functions through callServer(name, data, onOk, onErr) or await callServerAsync(name, data).
    4. Server functions read/write the sheet, update caches, and return plain JSON.

    Ground rules

    • There are no modules. Every .ts file is a global script; const/function at top level are visible everywhere. clasp uploads files alphabetically unless filePushOrder says otherwise.
    • Anything at top level that executes at load time must only use things already defined (see Constants & Config).
    • Server functions called from the client must be top-level, take one JSON-serialisable argument and return JSON-serialisable data (no Date objects).
    • Money is shown with two decimals but stored as plain numbers; sums that must be exact are done in integer cents (see the stats code).

    File load order (important)

    Apps Script evaluates files in the order clasp uploads them. The code is written so it is order-independent (Tier-0 constants are literals; Tier-1 settings resolve lazily at call time), and a test loads the sources in ten different orders to prove it. Still, set an explicit order in .clasp.json as a safeguard so the constants load first:

    {
  "scriptId": "…",
  "rootDir": "dist",
  "filePushOrder": ["utils/GlobalConsts.ts", "utils/Config.ts"]
}

    Files listed in filePushOrder go first; the rest follow alphabetically.

    Advanced services & scopes

    • Spreadsheet-bound script, V8 runtime.
    • Scopes used: spreadsheets, container UI, script app (triggers), and external request is not needed.
    • CacheService (document cache), PropertiesService and LockService are used; no advanced Sheets service is required.

    Triggers

    Create a time-driven trigger for recordDailyData (once a day, after school) to feed Historical Analytics. The function itself skips Sundays and Mondays and honours the logDaily setting.

    Deploy checklist

    1. npm run build.
    2. npx clasp push.
    3. Reload the sheet, open every dialog once, and run Clear Client Cache from Settings.
    Always smoke-test in a copy of the sheet before deploying to the live one.

    Student Portal

    A web app served by doGet() in utils/PortalUtils.ts, rendered by Portal.html with styles/Portal.html. appsscript.json declares executeAs: USER_DEPLOYING and access: DOMAIN.

    Security model

    • The caller is read only from Session.getActiveUser(). Nothing the browser sends decides who someone is.
    • Every endpoint re-checks the caller. Students may only use profiles linked to their email; admins (spreadsheet editors and owner) may act for any student that exists, under the same rules, and every such action is logged with the admin's email.
    • Student IDs are read on the server only to match an email and are never sent to the browser.
    • The allowed domain is the Script Property named by PORTAL_DOMAIN_PROPERTY, read through getPortalAllowedDomain() in Config.ts. It is never written in source. With no domain set, only admins can open the portal.
    • The page builds every element with textContent, so item names or student names can never inject markup.
    • Flood control, in two layers. The page sends server calls one at a time with a short gap, locks buttons for a cool-down after each action, waits until typing stops before searching, and refreshes itself only every 45 seconds when nobody is typing (constants at the top of the script in Portal.html). Because a page can always be bypassed, the server also limits each person with checkPortalRate_(): a minimum gap between actions and a per-minute cap for actions and for reads (PORTAL_ACTION_MIN_GAP_MS, PORTAL_ACTIONS_PER_MINUTE, PORTAL_READS_PER_MINUTE in GlobalConsts.ts).
    • Speed: working out which student an email belongs to used to read every period tab on every click. The roster (who is on which period, with their IDs) is now remembered for 5 minutes and cleared at once whenever the sheets are filled or the portal tabs are created, so a student added by hand to a period tab can take up to 5 minutes to appear. Balances, requests and history are always read live. The first account opens with the page's first answer, and an action sends the refreshed account back with its result, so the page does not make extra round trips. The history is checked with two tiny reads while the log has no new row.
    • Feedback on clicks: a button that sends something to the server turns into a disabled spinner with a busy label ("Investing...", "Approving...", "Opening account..."), and every action button on the page is locked until the action and its short cool-down are over. Cached actions such as paging, searching and switching tabs stay instant and are never locked (markButtonBusy, setWorking and actionButton in Portal.html).
    • The PORTAL_EXPERIMENTAL constant in GlobalConsts.ts controls the EXPERIMENTAL labels in Banking Settings and on the portal page. Set it to false to remove them.

    portalGetTransactionsowner of the profile, or adminEvery log row of that student, newest first, with a flag for purchases that were undone. Two sheet reads however long the log is (columns A to C, then one block), cached until the log gets a new row.
    portalDeposit, portalWithdrawowner of the profileCall handleDeposit / handleWithdraw with override always false. The withdrawal lockout, which the admin dialog only checks in its page code, is enforced here on the server.
    portalRequestExpenditure, portalCancelRequestowner of the profileWrite or cancel a row in the Expenditure Requests tab. Nothing is charged yet.
    portalAdminListRequests, portalAdminResolveRequest, portalAdminCompleteRequestadminApprove charges through applyMathToSelection on the Expenditures cell, inside the transaction lock.

    log() inside a web app

    There is no spreadsheet window to alert in a web request. While a portal action runs, portalCapturedMessages collects what log(message, true) would have alerted and the action returns it to the student. Outside the portal the behaviour is unchanged.

    Things to know

    • Pending requests count against Max/Person and Max/Class so students cannot queue more than the cap allows. Approval re-checks everything, since price, balance or caps may have changed.
    • The predictor is the same straight-line projection as Investment Banking: principal + principal x weekly rate x week, for the weeks left before investing ends.
    • Investing is refused outside the start and end investing dates when they are set.

    Workbook Contract

    The code assumes a specific sheet layout. Column indexes are 1-based. Their defaults live in GlobalConsts.ts as DEFAULT_*, the Settings sheet can override them, and code reads them only through the accessors in Config.ts (for example getNamesColumn()); never hard-code them or read DEFAULT_* directly.

    Required sheets

    SheetRole
    Period NOne per class period. Students start at getUserStartingRow() (default 7). Built from Template.
    TemplateCloned by the student importer.
    SettingsKey/value store (see Settings Pipeline).
    Main ServicesPrice list.
    TransactionsAppend-only log, columns A–P.
    Historical RecordsDaily snapshots. Archives are copies named Records_….

    Period sheet columns

    Column L (getStudentIdColumn(), setting studentIdCol) holds the hidden student ID, written as text so leading zeros survive; the import refuses to use it when it already holds anything that is not an ID. Positions come from the accessors getEarningsColumn(), getExpendituresColumn(), getNetInvestmentGainColumn(), getDepositDateColumn() and friends. Balance and net-income columns hold formulas; the code writes earnings, expenditures and investment inputs and lets the sheet compute the rest.

    The Services UI labels say "Column D" / "Column G" for earnings/expenditures but the code writes columns 3 and 5. This label mismatch is a known, unfixed issue (see Gotchas).

    Transactions sheet (A–P)

    16 columns (TRANSACTION_COLUMN_COUNT), one row per event, oldest at the top (row 2 onward; row 1 is the header). The newest transaction is the last row; the UI reverses it. mapTransactionRow in TransactionCache.ts is the single place that turns a raw row into the JSON shape the client uses, so change columns there and in GlobalConsts.ts only.

    Historical Records layout

    • Row 2 and 3: metric headers and column formulas that reference the period sheets.
    • Rows 3–10 / 11+: the formula row(s) used by the live snapshot, then recorded values appended below.
    • evaluatePeriodFormulas(ss, historySheet) in OnLoadData.ts evaluates the formula row against the period sheets with a cell-range regex; recordDailyData and the live analytics point both use it, so they always agree.

    Constants & Config

    Fixes the "constants depend on constants" loop. There are two tiers, and sheet reads happen only in the second.

    The old problem

    GlobalConsts.ts contained USER_STARTING_ROW = fetchProperty(…). That runs at load time and calls into SettingsUtils, which uses other constants and the settings loader. Depending on file order it hit a temporal-dead-zone ReferenceError, or the loader fell back to defaults and cached them. Adding more sheet-driven constants only made it worse.

    The two tiers

    TierWhereRules
    0, bootstrapGlobalConsts.tsPure literals only. No function calls, no sheet access, no reference to other files. Includes DEFAULT_USER_STARTING_ROW and all TRANSACTION_* cache tuning values.
    1, settings-drivenConfig.tsRead through getConfig(key) at call time, memoized, never at load time.
    // Usage
const startRow = getUserStartingRow();      // not a constant any more
const days = getConfig('withdrawLockoutTimeframeDays');

    How the loop is prevented

    • Call-time defaults. getAdvancedSettingDefinitions() is a function. A top-level object literal of defaults would reference GlobalConsts constants while Config.ts loads first alphabetically, causing the TDZ error again.
    • Re-entrancy guard. configResolving tracks keys being resolved. If resolving a key triggers a read of the same key (settings loader → config → settings loader…), the inner call returns the default instead of recursing.
    • Validation. Values pass a validator and coerceToNumber; invalid or missing values fall back to the default.
    • Memoization. Resolved values are cached until resetConfigMemo(), which setSettingsProperty() calls after any write.

    Every Settings key and its accessor

    All 25 "Advanced Technical Settings" on the Settings sheet are wired. The sheet value wins; if it is blank, invalid, or names a tab that does not exist, the DEFAULT_* literal is used and a line is written with log().

    Diagnosing "constants can't be read"

    Run verifyConstantsAreReadable() from the Apps Script editor. It prints, through log(), each key with the value found on the sheet, the value used, and why a default was chosen (blank cell, invalid value, missing tab). findBootstrapSettingMismatches() lists bootstrap cells that disagree with GlobalConsts.ts. Typical causes: a sheet-name setting that points at a tab that does not exist (for example "Services" instead of "Main Services"), or a blank cell.

    Code conventions

    • Always log through log(). Never call Logger.log or console.* in server code; only the log() implementation may.
    • Styles live in src/styles/. No <style> blocks, style="" attributes or element.style… in script elsewhere. Toggle visibility with setElementDisplay(element, 'none' | 'flex' | 'block') (classes in styles/DisplayState.html, included by every dialog).
    • Readable names. Descriptive variables and functions (transaction, blockNumber, timestampMs), no cryptic abbreviations.

    Rules for new constants

    1. Can it be a literal? Put it in GlobalConsts.ts (Tier 0).
    2. Does it come from the Settings sheet? Add a DEFAULT_* literal and an entry in getAdvancedSettingDefinitions, add an accessor, read it through that accessor at the point of use, never assign it to a top-level const.

    Settings Pipeline

    Read path

    fetchProperty(key, group) → load Settings sheet (cached) → find key → return a native typed value (number, boolean, string). On a load failure it returns {error} immediately instead of throwing.

    Rolling Transaction Cache

    The transaction log is cached in fixed-size blocks and only a moving window of them stays cached. Switching pages or tabs re-centres the window on what the admin is looking at, evicting the farthest blocks, much like lazy loading in a scrolling list.

    Blocks

    • Rows are grouped into blocks of TRANSACTION_BLOCK_SIZE = 50, anchored at the oldest row. Because the log is append-only, new rows only ever change the newest block; older blocks stay valid forever.
    • Each block is stored under TRANSACTION_BLOCK_KEY_PREFIX + blockNumber with its row count. On read, a block whose cached count differs from the expected count is treated as stale and re-read.
    • The index (TRANSACTION_INDEX_KEY) lists cached blocks with a last-used stamp and the total row count. Index writes are guarded by a LockService lock to avoid lost updates between concurrent dialogs.

    Budgets

    ConstantDefaultMeaning
    TRANSACTION_BLOCK_SIZE50Rows per block.
    TRANSACTION_CACHE_MAX_BLOCKS24Hard cap on cached blocks (1200 rows).
    TRANSACTION_CACHE_MAX_BYTES1,200,000Soft cap on total cached bytes.
    TRANSACTION_PREFETCH_BEHIND_PAGES1Pages kept behind the viewed page.
    TRANSACTION_PREFETCH_AHEAD_PAGES2Pages kept ahead.
    TRANSACTION_MAX_PAGE_SIZE200Largest page the UI may request.

    The sheet can hold any number of rows; only the budget above is ever cached, so the cache limit can no longer be hit however large the log grows.

    Planning the window

    planTransactionWindow(total, page, pageSize, direction) is a pure function returning the block range to keep:

    • forward (moving to higher page numbers, i.e. older): keep more ahead than behind.
    • backward: the mirror image.
    • jump (not adjacent to the last page): symmetric.
    • If the window would run past either end of the log, the unused slack is given to the other side so the budget is always used.

    chooseTransactionEvictions(index, window, budget) returns blocks to drop: never any block inside the window; otherwise farthest from the window first, least recently used breaking ties.

    Client side

    RollingTransactionLog (TransactionWindow.html):

    const log = new RollingTransactionLog();
const res = await log.getPage({ page: 3, pageSize: 20, filters: {}, includeStats: true });
// res: { rows, page, pageSize, totalRows, totalPages, stats? }
    • The server returns a whole window (newest first). The client keeps it in RAM and serves pages that fall inside it with no server call.
    • Moving outside the window calls fetchTransactionsPage; with filters set it calls queryTransactions.
    • A debounced background _scheduleRoll(direction) re-centres the window after the user settles on a page. The direction is captured before lastPage is updated (an earlier bug made every roll a "jump").
    • seq / appliedSeq sequence numbers discard responses that arrive out of order.
    • invalidate() drops the RAM window; call it after writes made from the same dialog.

    Filtered queries

    Filters (student substring, type, period, from/to ms, field scope, ids) are evaluated server-side by matchesTransactionFilters. Because arbitrary filters can't use the block cache, queryTransactions scans the sheet in slices of 1000 rows, so memory stays bounded. Facets (distinct periods/students/types) come from fetchTransactionFacets, are cached, and respect the current date range. Unfiltered stats (getUnfilteredTransactionStats) are maintained incrementally in integer cents.

    Tuning

    • Slow page flips: raise TRANSACTION_PREFETCH_AHEAD_PAGES.
    • Cache errors or quota pressure: lower TRANSACTION_CACHE_MAX_BLOCKS or TRANSACTION_CACHE_MAX_BYTES.
    • Wide sheets or long reasons: reduce TRANSACTION_BLOCK_SIZE so a block stays far below 100 KB.
    • Check state with getTransactionCacheStatus(); prime with preloadTransactionCache() (called from preloadCacheForAllDialogs).

    Transactions & Undo

    Appending

    Every write path (balance edits, services, investments) appends a row via TransactionsUtils.ts, then calls onTransactionsAppended() so the newest block, the index and the stats stay correct without a full invalidation.

    Undo

    Undo takes transaction ids, loads exactly those rows with fetchTransactionsByIds(ids) (it does not load the full log), applies the inverse using transactionBalanceChange, and appends a new "Undo transaction ID …" row. Originals are never edited or deleted.

    Reset

    "Clear All Transaction Records" clears the sheet and calls invalidateTransactionCache().

    Anything that edits the Transactions sheet outside these functions (manual edits, imports) must call invalidateTransactionCache(), otherwise cached blocks may be stale until their row count changes.

    Quarter Resolution

    The previous getCurrentQuarter looked up the wrong settings keys, so it returned Q1 forever. Resolution now lives in QuarterUtils.ts.

    Rules

    1. Read startQ1Date…endQ4Date (the legacy startQuarterOneDate style keys are also accepted).
    2. If now falls inside a quarter, that quarter is current. An end date at exactly midnight is treated as inclusive for the whole day.
    3. In a gap (break), the quarter that most recently started wins.
    4. Before Q1 starts: Q1. After Q4 ends: Q4. If nothing is configured: Q1 with status unconfigured.
    resolveCurrentQuarter(dates, nowMs, midnightCheck) // pure function
getCurrentQuarterInfo(data?)                        // server endpoint

    The endpoint returns { quarter, status, ... } where status is one of in-quarter, between, before, after, unconfigured.

    Client behaviour

    • getActiveQuarter() asks the server (callServerAsync('getCurrentQuarterInfo')) and falls back to the cached settings plus a local getCurrentQuarter(dates, nowMs) if the call fails.
    • autoConfigureCurrentQuarter() sets the income/expense dropdowns on load.
    • startQuarterWatcher() re-checks every 5 minutes and on window focus / visibility change.
    • quarterManuallyChosen stops the watcher from overriding a quarter the admin picked.
    • populateLists uses a per-list quarter (quarterIncome / quarterExpense).

    Investments Engine

    Interest maths

    weeks    = floor(daysSinceDeposit / 7)
gross    = deposit + deposit * weeklyRate * weeks      // simple, not compound
net      = gross - (gross - deposit) * withdrawalTax   // tax on the gain
CoD      = net   (stored in NET_INVESTMENT_GAIN_COL)

    handleDeposit rules

    Server (InvestmentUtils.ts) and client (InvestmentsManager.html) enforce the same rules; the server is authoritative.

    1. Read the net CoD from NET_INVESTMENT_GAIN_COL.
    2. If a CoD exists and no override, check the lockout: withdrawLockoutTimeframeDays (default 14) after DATE_DEPOSIT_COL. Inside the window: log a warning, return false.
    3. availableFunds = balance + CoD (previously only the balance was checked, causing the "you have less than you do" bug).
    4. Unless override: if amount > availableFunds, refuse with a message containing "isn't possible" and the total available.
    5. Otherwise cash out the CoD, subtract the amount from the combined pool, record the new deposit and date.

    Client-side, getAvailableDepositFunds(student) returns cash, CoD and total for the alert text; handleDepositCashWithCoD fills in cash + CoD, alerts if the CoD is locked, and no longer returns silently when cash is 0. The old client code added the CoD to the amount a second time (totalAmount = codAmount + depositAmount); that is removed.

    Analytics Pipeline

    Server: fetchHistoricalRecordbookData

    Returns { headers, records, meta }.

    1. Collect the live Historical Records sheet (always, by name) plus every Records_… archive.
    2. De-duplicate on timestamp|period (archives overlap the live sheet). Count removed duplicates in meta.duplicatesRemoved.
    3. Sort chronologically.
    4. Compute a live snapshot under a script lock using evaluatePeriodFormulas; mark those records live: true. If this fails, meta.liveError is set and the stored history is still returned.

    Record shape: { day, ts, date, dateStr, sheet, live, source, metrics }. day is computed in the spreadsheet's time zone.

    Client

    • getVisibleRecords() filters by date range, honours #includeLive, and keeps the newest snapshot per day per sheet (so a re-run of the daily job doesn't double-count).
    • renderChart groups by day; combined scope sums periods, average scope averages them. Live days are labelled "(live)" and drawn as larger diamonds.
    • showDataNotice() shows #dataNotice for meta.liveError or empty data.

    Why "current records" were missing

    The old code read only archived snapshot tabs and ignored the current Historical Records sheet and the not-yet-recorded present values. Both are now included.

    Conventions, Gotchas & Known Issues

    Conventions

    • No module syntax; no top-level work that depends on another file.
    • Use getUserStartingRow(), never a constant, for the first student row.
    • Parse dates from settings with the helpers in QuarterUtils.ts; don't call new Date(str) on sheet strings directly.
    • Return plain data from server endpoints; convert dates to ms or ISO strings.

    HTML templating

    Apps Script treats a literal <? in an HTML file as a template scriptlet, even inside <pre> or a JS string. Write &lt;? in docs, or split the string in JS ('<' + '?').

    Known issues (not fixed)

    • resetAll is never defined, so the Settings "Reset ALL Sheets" button does nothing.
    • The Services UI labels refer to "Column D" and "Column G", but the code uses EARNINGS_COL = 3 and EXPENDITURES_COL = 5.
    • The latest changes have not been verified against a real spreadsheet; smoke-test in a copy first.

    Performance Notes

    Almost all run time in Apps Script is per-call overhead (each range read/write, each spreadsheet lookup, each client→server round trip). These are the rules the code follows to keep that low.

    Batch every range operation

    • Read a table with one getValues() and index into the array; write with one setValues(). Never call getRange(...).getValue() in a loop.
    • fetchServicesData reads the whole price table in one call; writeInvestmentsDataToSheet reads and writes each period's input block once and keeps formulas in rows it does not change.
    • When you only need names, read the names column, not getDataRange().

    Per-execution sheet handles

    SheetMemo.ts provides getSS(), getAllSheets() and getSheetNamed(name), which fetch from the spreadsheet once per execution. Never call SpreadsheetApp.getActiveSpreadsheet() directly. Any code that adds, deletes, renames or copies a sheet must call resetSheetMemo() afterwards.

    Targeted cache refresh

    • fetchInvestmentsDataCached({ forceRefresh: true, periods: ['Period 3'] }) re-reads only those sheets and serves the other periods from cache. It silently falls back to a full refresh when the cache is cold or a period is unknown.
    • Cache reads and writes for several keys use getAll / putAll. setCachedData skips the property write when the stored copy is identical.
    • clearServerCacheValues(keys) is the batched version of clearServerCacheValue; the client sends it once, a couple of seconds after a dialog opens.

    Background cache warming

    WarmCache.ts: enableCacheWarming() installs a 10-minute time trigger for warmCaches(); disableCacheWarming() removes it. warmCaches() calls the normal cached fetchers without forceRefresh, so it only reads what has expired, skips when another operation holds the script lock, and never writes to a sheet.

    Incremental views of the transaction log

    The expenditure notes and the Max/Person / Max/Class counts are views of the log. Instead of reading the whole log every time, each view is cached (expenditureNoteRecords:<student|period>, serviceLimitRecords:<quarter>:<item hash>) with the number of log rows it covers and the id on its last covered row. Later calls only read the rows added since. An entry is thrown away, and the log read in full once, when the log has fewer rows than the entry covers, the id on that row no longer matches (the log was cleared or rewritten), or (for limits) the quarter dates changed. Rebuild Expenditure Notes always reads the full log. A student with no expenditures in the log has no entry, so their first purchase takes the full read once.

    Transaction lock

    Everything that moves money or appends to the log (executeBalanceAction, executeServiceAction, undoTransactions, handleDeposit, handleWithdraw, addTransactionRecords, resetAllTransactionRecords, Rebuild Expenditure Notes) runs through runWithTransactionLock in LockUtils.ts. It uses the document lock so it never mixes with the script lock the caches use, and nested calls in the same execution reuse it. Two admins acting at once are serialised: no lost update, no duplicate transaction id, and a cap cannot be passed twice. A call that waits more than 30 seconds gives up without changing anything.

    Client start-up

    • Independent requests start together: in the Services dialog the transaction log, sheet names, quarter and price list; in Investments the ledger and settings (Promise.all).
    • fetchClientData makes one server call per cache miss; the old write-back call to setServerCacheValue was removed because the server fetchers already store what they return.
    • Analytics draws stored history first (fetchHistoricalRecordbookData with includeLive:false), then adds the live point from fetchLiveHistoricalPoint. Transaction Records requests the first page before the filter facets.

    Cookbook

    Add a new setting

    1. Add the row to the Settings sheet template and the card in SettingsManager.html.
    2. Add a default in getConfigDefault if code reads it.
    3. Read it with getConfig('key'); never at load time.

    Add a Transactions column

    1. Update TRANSACTION_COLUMN_COUNT and the column constants.
    2. Extend mapTransactionRow and, if filterable, matchesTransactionFilters.
    3. Append the value where rows are created in TransactionsUtils.ts.
    4. Run Clear Client Cache after deploying so stale blocks are rebuilt.

    Add a server endpoint

    1. Write a top-level function taking one JSON-able argument.
    2. Call it with callServerAsync('name', payload).
    3. Return only plain data; wrap errors as { error: message }.
